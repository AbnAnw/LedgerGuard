# ADR-0004: Checked string values for lifecycle states

- **Status:** Accepted
- **Date:** 2026-10-07
- **Decision owners:** LedgerGuard engineering

## Context

LedgerGuard has many lifecycle and classification values. Native PostgreSQL enum types provide strong validation but require type-level migrations for every added value and are awkward to remove or reorder. Application-only validation would allow invalid values through direct database writes.

## Decision

- Represent lifecycle/status values as bounded `VARCHAR` columns with named database `CHECK` constraints generated by SQLAlchemy's non-native enum support.
- Represent the same values as Python string enums for typed application use.
- Treat values documented in `DATA_MODEL.md` as stable API and evidence vocabulary; renames require an explicit data migration.
- Add or remove a value through an Alembic migration that replaces the named check constraint in the same deployment sequence as compatible application code.

## Consequences

- PostgreSQL rejects unknown values while schema evolution remains ordinary transactional DDL.
- Values remain human-readable in queries, exports, and audit evidence.
- The application and migration must share the exact lowercase values, which metadata and migration tests will verify.
- This choice does not replace service-level transition validation; a valid state value may still be an invalid transition.

## Alternatives rejected

- **Native PostgreSQL enums:** strong and compact, but operationally rigid for an evolving 21-day product model.
- **Unconstrained strings:** easy to change but allow invalid states and weaken reporting integrity.
- **Lookup tables for every status:** flexible but adds joins and mutable reference data for values that are part of the code contract.
